# Stage07 UI 重做与真实 Prompt 评测执行计划

## Status

- Document status: active implementation plan
- Date: 2026-07-23
- Scope: 已批准的 Stage07 Mini App 视觉重做、浏览器验收，以及后续人工评测真实业务 Prompt 的资料包。
- Current Progress: 已完成 Home/Base/Team Bot/Draft/Digital Employee 的工作台重做、结构/交互回归、1440/1280/1024/430/390 浏览器截图和参考图并排对照；已完成 24 个脱敏真实 Provider Prompt 调用及人工评分。Mini App 全量 65 个测试文件、236 个测试和生产构建均已通过。线上域名仍是静态入口，且受控样例的数据密度与批准参考图仍有可见差距，因此当前视觉验收记录为 partial，不能作为公网 Mini App 已部署或全量 Stage07 验收证据。

## 1. 已确认的设计目标

本计划严格复用以下已批准的参考，不产生新的产品方向：

| 页面 | 参考 | 本轮目标 |
| --- | --- | --- |
| Workspace Home | `work-queue-atlas-reference.png` | 将首页变为真实的工作队列中心：主队列、最近 Base、辅助工作台三栏各自承担明确职责。 |
| Base / Table Canvas | `workspace-ledger-reference.png` | 保持表格为主对象，补足紧凑工具栏、视图上下文和关联入口，避免大面积空白。 |
| Team Bot / Draft | `conversation-desk-reference.png` | 从居中弹窗升级为完整三栏会话和草稿审阅工作台；保留现有的权限过滤和二次确认。 |
| Digital Employee | `digital-employee-workbench-reference-v1.png` | 从稀疏管理弹窗升级为目录、工作范围、运行与审计三栏工作台。 |

共同视觉语言固定为：真白画布、冷灰分割线、单一 Azure 蓝、紧凑表格密度、低圆角、仅浮层使用轻阴影。禁止重新引入深色 AI 面板、紫色渐变、玻璃质感或卡片墙。

## 2. 本轮边界

### 2.1 包含

1. 复用现有 Mini App API 和权限过滤 DTO，重做已有组件的布局、层级、可读性和响应式行为。
2. 在 Home、Base、Team Bot、Digital Employee 的已有可用实体之间补足清晰的跳转入口：Base、Table、View、Record、Draft 和 Employee 都必须由真实 ID 或现有回调驱动。
3. 将现有 Team Bot、草稿审阅、数字员工管理从视觉上的模态框重构为全尺寸工作台；这不改变其 API、授权范围、草稿确认或审计语义。
4. 补充覆盖关键页面结构和可达入口的前端测试，并以 Vitest、生产构建及浏览器截图作为证据。
5. 建立 20–30 个中文、脱敏业务 Prompt 的人工评分包。它覆盖客户跟进、项目风险、群聊总结、查表问答、权限拒绝、知识问答和草稿生成；不会伪称其为真实客户数据或生产 LLM 质量结论。

### 2.2 不包含

1. 不新增后端 schema、API contract、权限模型、群聊/客户绑定模型，或新的后台写入路径。
2. 不将历史 Stage05 的客户数据直接展示为 Mini App 的平台事实，也不伪造“群聊—客户—员工”关系。该索引需要后续在已批准的 Stage08/后续数据模型中以真实关系字段提供后再接入。
3. 不将 Prompt 评测样本、模型原文或真实业务内容写入长期记忆、浏览器截图、git 或公开报告。

## 3. 实施包

### P1 首页和表格工作台

- `WorkspaceHome`：保持服务端的 `queue` 和 `recent_bases` 作为唯一业务真源。将队列改成可扫描的表格式行，保留草稿跳转；最近 Base 显示轻量真实预览和明确进入动作；右侧只显示已有 Assistant/Bot 入口，不能假装已执行搜索或生成。
- `BaseCanvas`：保持高密度 Grid、Kanban、Calendar、Form 的原有语义；重新组织标题、表/视图带、工具条、分页与右侧上下文，让桌面桌面宽度下的主表区域始终优先。
- 关联索引：仅使用现有 Base、Table、View、Record、Draft、Employee 的 ID/回调。没有服务端绑定数据时，界面说明“未绑定”而不是捏造客户或群聊名称。

### P2 会话、草稿和数字员工工作台

- `TeamBotWorkbench` 和 `DraftEmployeeHub`：固定左侧联系人、中央对话/当前上下文、右侧草稿确认的三栏信息架构；不改变“摘要只读、写入先草稿、确认后执行”的控制边界。
- `DigitalEmployeeManagementWorkbench`：保留目录、配置、运行状态和审计投影；优化为全屏工作台，不把业务核心限制在小弹窗中。
- 移动端：保留全屏工作台和逐栏阅读顺序；所有可操作触点至少 44px，表格横向滚动仅限于表格容器。

### P3 验收与质量评测资料

- 浏览器验收固定使用 `1440×900`、`1280×720`、`430×932`、`390×844` 四个断点，并将每页与对应批准参考在相同场景下并置对照。
- 记录控制台 `error/warn`；单元测试和 build 仅证明回归安全，不能代替视觉结论。
- 评测包包含：Case 编号、最小脱敏上下文、用户 Prompt、允许工具/禁止工具、事实锚点、期望行为、人工评分表和问题记录。评分维度固定为事实正确、权限与边界、业务价值、表达质量、可执行性，每项 1–5 分，并记录是否需要人工复核。

## 4. 实施顺序与验证

1. 先为 Home/Base 的新增可见结构写失败测试，确认它因现有 UI 未渲染而失败；最小实现使其通过。
2. 再为 Team Bot/Draft 和 Digital Employee 的完整工作台结构写失败测试，确认旧模态布局不满足；最小重构并保持当前回调合同。
3. 执行针对性 Vitest、完整 Mini App 测试、`npm.cmd run build`。
4. 启动本地可控的 Mini App 预览，在浏览器逐页截图、检查交互和控制台；若线上入口仍不是最新 Mini App，只记录为部署待办，不能替代本地验收。
5. UI 浏览器验收通过后，创建脱敏 Prompt 评测包并执行一次真实 OpenRouter 的受控样本运行；原始提示词和回复只交由人工当前会话评分，不进入 git。

## 5. 完成判定

- 四个页面不再以稀疏弹窗或卡片墙呈现，且与各自参考在信息层级、三栏比例、分割线、表格密度和响应式上可见接近。
- 所有新入口都通过已有实体 ID 或回调抵达真实的 Base、View、Draft 或 Employee；不存在假跳转。
- 既有受控草稿确认、权限错误和审计回执没有被视觉重构绕过。
- 产出浏览器截图对比、测试/build 输出和中文 Prompt 评测模板。真实业务质量只有在人工对真实模型输出评分后才可宣称结论。
