## 4. 需要修复的模型层问题

1. **结构化输出不稳**：C01、C03、C05、C10 出现截断或非 JSON 输出。上线前应将 Provider 输出改为强制 JSON Schema/结构化响应，并在解析失败时走一次不带业务执行的修复提示；修复仍失败则安全降级，不能把半截文本交给用户。
2. **路由语义需与网关区分**：C07、C15、C21 将“正常查表”“字段缺失”“知识 SOP”错误归类为拒绝或查表。建议在 LangGraph 路由节点增加少量 hard rules：有授权表证据但字段缺失 = `lookup_table` 后说明缺口；有版本化知识证据 = `knowledge_search`；不因“管理摘要”自动拒绝。
3. **禁止虚构执行完成**：C04 在直连评测中说“已生成草稿”，但本次只测试模型回复，没有实际创建草稿。生成层需要固定用语：`建议创建以下草稿，确认后由系统执行`，只有收到持久化回执时才能用“已生成”。
4. **拒绝答复的替代建议要收敛**：C16 的替代建议不应暗示能绕开隐藏字段。拒绝后的建议必须仍然在显式授权范围内。

## 5. 结论

本轮已得到真实 Provider 的 24 个业务场景回答，说明模型在权限拒绝、事实查表、群聊边界和多字段草稿上有可用基础；但 `83.3%` 的结构化输出率和 `70.8%` 的路由命中率不足以称为“业务质量验收通过”。下一开发优先级是结构化输出闸门、确定性路由补强和执行状态措辞约束，之后以同一套 24 Case 复测。

该结论不等于 Telegram、Mini App、工具执行或生产上线验收通过。
