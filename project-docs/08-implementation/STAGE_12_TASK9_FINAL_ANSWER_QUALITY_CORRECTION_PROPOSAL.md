## 1. Proven Gap

1. `RuntimeAnswerTrace` contains only `rendered_answer` and `claims`.
2. `AnswerScore` checks grounded Claim precision, required record recall and aggregate equality only.
3. It does not directly score instruction/action satisfaction, Chinese clarity, or refusal/degradation appropriateness, although the correction source of truth requires all three for every Case/round.
4. `compose_claim_graph(graph)` currently uses a deterministic flat fact list in the isolated A–F runner.

## 2. Recommended Minimal Correction

Keep the existing authorized Query, typed facts, ClaimGraph, Action admission, database, public API and production flags unchanged. Correct only the isolated Composer and evaluation boundary.

### 2.1 Provider returns a bounded Answer Plan

Replace free factual prose in the Composer Provider response with `ComposerAnswerPlanV2`:

```text
ComposerAnswerPlanV2
-> sections[]
   -> section_kind
   -> objective_ids[]
   -> claim_ids[]
   -> action_slot_ids[]
   -> connector_code
-> ordering only
```

Allowed `section_kind` values are bounded to summary, facts, risks, daily, actions, denial and degradation. `connector_code` is an enum owned by the deterministic renderer. The Provider may select and order only IDs already present in the authorized ClaimGraph and action/objective statuses. It cannot provide new factual text, record IDs, values, citations or completion claims.

### 2.2 Deterministic renderer remains the factual owner

The renderer:

- converts selected Claim values to approved Chinese factual sentences;
- emits claim-to-evidence citations;
- renders each Action as pending, denied, conflicted or deferred;
- explicitly says no write/send occurred where required;
- renders permission denial and optional failure/degradation with approved Chinese templates;
- rejects omitted required objectives, claims, aggregates or Action statuses;
- rejects unknown/duplicate IDs and unsupported section combinations.

This preserves the Stage12 invariant: Provider controls ordering and bounded presentation; deterministic code owns factual text and safety statements.

### 2.3 Renderer emits an independently checkable receipt

Add `FinalAnswerRenderReceiptV1` to the internal Composer/runtime trace:

```text
covered_objective_ids[]
covered_claim_ids[]
covered_action_slot_ids[]
citation_edges[]
section_kinds[]
disclosure_codes[]
language = zh-Hans
```

The receipt is generated by the renderer, not trusted from the Provider. Its hash is bound to the answer, ClaimGraph hash, scope hash and Action status set.

### 2.4 Final answer hard gate

Add `FinalAnswerQualityScoreV2` with non-compensable dimensions:

1. `factual_correctness`
2. `required_result_completeness`
3. `relation_aggregate_correctness`
4. `citation_to_fact_grounding`
5. `instruction_action_satisfaction`
6. `chinese_clarity`
7. `refusal_degradation_appropriateness`

`gate_pass` is true only when every applicable dimension passes. It is never an average. `CaseScoreV2.release_gate_pass` and `FinalCampaignSummaryV2.release_gate_pass` must require this final-answer gate in addition to existing safety gates.

Chinese clarity is checked on the actual rendered answer: valid simplified-Chinese content, no mojibake/replacement characters, no raw JSON-only response, bounded length, non-empty labelled sections and no duplicated section body. The campaign artifact retains the complete answer and per-dimension reason codes for all 144 executions so the result remains manually reviewable.

## 4. Acceptance Criteria

- RED/GREEN tests prove a fluent but instruction-incomplete answer fails.
- A grounded answer that omits one required Action status fails.
- A denial Case that sounds successful fails.
- A degraded Case that hides degradation fails.
- A Chinese-looking raw JSON or mojibake answer fails.
- An answer with the right citation ID but the wrong Claim value fails.
- A valid reordered/grouped Answer Plan passes without allowing new factual prose.
- The raw execution request still contains only Query, round ID and isolated runtime context.
- No Gold, target, field, value or expected Action reaches the execution Provider.
- No production activation or external effect occurs.
