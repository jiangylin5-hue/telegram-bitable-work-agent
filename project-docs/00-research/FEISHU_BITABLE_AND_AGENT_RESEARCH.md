# 飞书多维表格与多维表格智能体调研

## Status

- Document status: research draft
- Scope: 飞书多维表格、AI 能力、智能体产品抽象、对 Telegram 多维表格和工作智能体项目的启发
- Research date: 2026-07-04
- Current Progress: 2026-07-04 完成第一版公开资料调研和项目落地启发整理。

## 1. 调研结论

飞书多维表格的核心不是“更好看的 Excel”，而是把表格、轻量数据库、多视图、权限、自动化、API 和 AI 能力组合成一个业务系统搭建平台。

对本项目最重要的启发是：

- 数据必须结构化：客户、账户、消息、服务草稿、服务记录、充值、风险、审计不能混在一张大表里。
- 同一批数据要支持多视图：表格、看板、仪表盘、待办队列、详情页、审计视图。
- AI 必须绑定业务数据和权限：AI 不是单独聊天，而是围绕表格记录、字段、上下文和业务规则工作。
- 自动化必须有边界：AI 可以识别、整理、生成草稿、提醒、汇总，但真实资金和账户写入必须走受控服务和人工确认。
- 外部系统要通过 API/工具接入：Telegram、后端服务、队列、审计日志和智能体需要围绕统一业务对象协作。

## 2. 官方可确认的信息

### 2.1 飞书多维表格定位

飞书官方产品页将多维表格定位为 AI 驱动的表格与业务系统搭建平台。这个定位说明它不是单一数据表工具，而是面向业务流程搭建、协作和自动化的工作台。

对本项目的含义：

- 我们要模仿的是“业务系统搭建机制”，不是单纯 UI。
- Telegram 只是入口之一，多维表格底座必须由后端数据模型、视图模型和权限模型支撑。

### 2.2 多维表格 AI 侧边栏

飞书帮助中心有“多维表格 AI 侧边栏”相关文档。AI 侧边栏体现的是：AI 不只是脱离业务数据的聊天窗口，而是可以围绕当前多维表格上下文提供总结、分析、生成和辅助操作。

对本项目的含义：

- Telegram 工作智能体应有上下文：当前客户、账户、服务记录、消息来源、字段状态、权限范围。
- AI 输出应尽量落为结构化对象，例如 `service_draft`、`risk_summary`、`daily_report`，而不是只输出一段聊天文本。

### 2.3 飞书开放平台多维表格 API

飞书开放平台提供多维表格相关 API，例如围绕 app、table、record 的接口能力。这说明成熟的多维表格产品会把表格、字段、记录、视图作为可编程资源，而不只是前端界面。

对本项目的含义：

- 当前项目应设计自己的内部多维表格资源模型：`base`、`table`、`field`、`view`、`record`、`automation`、`agent_action`。
- 即使第一版 UI 简单，底层也应为后续 API 化、自动化和智能体工具调用预留结构。

## 3. 关于“多维表格智能体”的判断

截至本次调研，公开可稳定核验的官方材料更常见的表述是“多维表格”“多维表格 AI 侧边栏”“开放平台多维表格 API”等；如果用户看到的是飞书产品内或发布会里的“多维表格智能体”新入口，公开网页资料未必完整覆盖该名称。

因此本项目暂时把“多维表格智能体”抽象为：

```text
绑定在多维表格业务数据、权限、自动化和外部工具上的 AI 数字员工。
它能读表、理解消息、生成结构化草稿、触发提醒、汇总日报、解释证据；
但不能越权直接执行高风险写入。
```

它和普通 AI 聊天机器人的区别：

| 能力 | 普通聊天 AI | 多维表格智能体 |
| --- | --- | --- |
| 数据上下文 | 依赖用户临时描述 | 绑定客户、账户、服务记录、消息和审计数据 |
| 输出形态 | 文本回答为主 | 结构化草稿、字段更新建议、任务、提醒、报告 |
| 权限边界 | 容易模糊 | 必须跟随表、字段、记录、动作权限 |
| 工作流 | 一问一答 | 可围绕状态机持续推进 |
| 审计 | 通常弱 | 每次建议、确认、执行、失败都应可追踪 |

## 4. 对 Telegram 项目的产品启发

Telegram 不适合承载复杂多维表格本体，但非常适合做入口、提醒、审批和轻交互。

推荐产品结构：

```text
Telegram Bot / Group / Mini App
-> message ingestion
-> AI intent extraction
-> multidimensional business records
-> draft queue / task board / dashboard
-> human confirmation
-> controlled backend execution
-> audit log and Telegram result callback
```

第一版重点不应是“在 Telegram 里画出完整飞书”，而应是：

- Bot 读取授权群消息。
- AI 从消息里识别客户、账户、金额、邮箱、动作类型和缺失信息。
- 系统生成服务草稿，而不是直接执行。
- Mini App 或 Web 展示多维表格视图、待办和确认队列。
- 员工确认后由后端受控服务执行。
- 所有结果写入 audit 和 execution log，再回传 Telegram。

## 5. 建议效仿的产品机制

| 飞书机制 | 本项目对应设计 |
| --- | --- |
| 多表结构 | 客户、账户、Telegram 消息、草稿、服务记录、充值、风险、审计分表建模 |
| 字段类型 | 金额、状态、人员、日期、附件、关联记录、单选、多选、公式、敏感字段 |
| 多视图 | 客户总表、账户资产表、服务看板、充值视图、风险仪表盘、Telegram 收件箱 |
| 权限 | 记录权限、字段权限、动作权限、视图权限、Agent 权限 |
| 自动化 | 状态流转、SLA 提醒、日报、异常升级、重复请求拦截 |
| AI 侧边栏/智能体 | 草稿生成、消息摘要、风险解释、日报生成、客户回复草稿 |
| API 化资源 | 内部定义 base/table/field/view/record/action/job，方便未来开放工具调用 |

## 6. 建议不要照搬的地方

- 不要先做一个通用无代码平台。当前业务目标是广告代理商工作流，不是做飞书竞品。
- 不要把多维表格理解成一张万能大表。复杂业务必须拆对象和关系。
- 不要让 AI 直接拥有系统管理员权限。
- 不要把 Telegram 群成员身份直接等同于系统权限。
- 不要在第一版追求所有视图、自动化和智能体能力齐全。
- 不要把充值、收款、余额回读混为一个状态。

## 7. 第一阶段产品建议

第一阶段建议只做一条闭环：

```text
Telegram 群消息
-> AI 识别客户充值/下户/绑卡需求
-> 生成服务草稿
-> 多维表格待确认队列
-> 员工确认或补资料
-> 后端受控执行或 blocked
-> execution log / audit
-> Telegram 回传结果
```

优先业务切片建议仍是充值流程，因为它同时涉及销售、财务、生产、权限、金额、执行日志和余额回读，最能验证系统价值。
